# Blueprint — Workshop con problemas reales

## Promesa

En 45-60 minutos, una persona verá cómo ai-engineering transforma trabajo ambiguo de proyecto en una cadena gobernada: explorar, preguntar, decidir, planificar, construir, revisar y explicar.

## Problemas que queremos enseñar

| Módulo | Problema real | Skill principal | Artefacto que debe quedar |
|---|---|---|---|
| 1 | “No conozco este repo y tengo que tocarlo sin romperlo” | `/ai-explore` | Mapa del sistema + riesgos |
| 2 | “La petición de negocio está mal definida” | `/ai-brainstorm` | Spec con decisiones y no-goals |
| 3 | “Necesito que la IA implemente sin saltarse TDD” | `/ai-plan` + `/ai-build` | Plan con tareas RED/GREEN/REFACTOR + tests |
| 4 | “No me fío del diff generado” | `/ai-review` | Findings accionables, severidad y owner |
| 5 | “Ahora tengo que entender lo que se ha construido” | `/ai-explain` | Explicación con file:line anchors |
| 6 | “Tenemos un reto abierto y tiempo limitado” | cadena completa | Demo navegable + retrospectiva |

## Criterio de calidad del workshop

El asistente debe salir con una idea concreta: **ai-engineering no es un generador de código; es un sistema de control para que agentes de IA puedan trabajar dentro de reglas de ingeniería.**

## Cómo empaquetar cada problema

Cada ejercicio público debe tener:

1. Contexto del problema.
2. Repo o carpeta objetivo.
3. Prompt inicial recomendado.
4. Qué preguntas buenas debería hacer el agente.
5. Artefacto esperado.
6. Criterio de demo.
7. Riesgos y trampas para debatir.
8. Variante stretch.
